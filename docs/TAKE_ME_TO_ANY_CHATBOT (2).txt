Polymorphism
 •   It   is   the   ability   to   redefine   a   function   or   object   in   more
 than   one   form .
 •   Polymorphism   can   help   to   make   programs   more
 flexible   and   easier   to   maintain ,   because   it   allows   for

 •   Same   name,   Different   behavior
C# | Method Overloading
 •   Method   Overloading   is   the   common   way   of   implementing
 polymorphism .
 •   A   user   can   implement   function   overloading   by   defining   two   or
 more   functions   in   a   class   sharing   the   same   name .
 •   C#   can   distinguish   the   methods   with   different   method   signatures .
 •   i . e .   the   methods   can   have   the   same   name   but   with   different
 parameters   list   (i . e .   the   number   of   the   parameters,   order   of   the
 parameters,   and   data   types   of   the   parameters)   within   the   same
 class .

 •   If   we   need   to   do   the   same   kind   of   the   operation   in   different   ways   i . e .
 for   different   inputs .

Using abstract classes and abstract methods

Abstract Classes

Encapsulation pattern
 •   Problem :   Exposed   fields   are   directly   manipulated   from
 outside,   leading   to   undesirable   dependences   that   prevent
 changing   the   implementation .
 •   Solution :   Hide   some   components ,   permitting   only   stylized
 access   to   the   object .
Subclassing pattern
 •   Problem :   Similar   abstractions   have   similar   members   (fields
 and   methods) .   Repeating   these   is   tedious,   error - prone ,   and   a
 maintenance   headache .
 •   Solution :   Inherit   default   members   from   a   superclass ;   select
 the   correct   implementation   via   run - time   dispatching .
Iteration pattern
 •   Problem :   Clients   that   wish   to   access   all   members   of   a
 collection   must   perform   a   specialized   traversal   for   each   data
 structure .
 •   Solution :   Implementations   perform   traversals .   The   results
 are   communicated   to   clients   via   a   standard   interface .
Exception pattern
 •   Problem :   Code   is   cluttered   with   error - handling   code .
 •   Solution :   Errors   occurring   in   one   part   of   the   code   should
 often   be   handled   elsewhere .   Use   language   structures   for
 throwing   and   catching   exceptions .

Static   method
 •   In C#, a static method is a   member that belongs to the class itself rather
 than to a specific instance (object)   of the class.
 •   This   means you can   call the method directly using the class name   without
 creating an object.
 •   Key   Features
 •   No Instantiation : You cannot create an object of a static class using the new keyword .
 •   Direct Access : Members are accessed directly via the class name (e.g.,
 ClassName.MethodName ()).
 •   Static Members Only : All fields, methods, properties, and events within the class
 must also be declared as static.
 •   Implicitly Sealed : It cannot be inherited by another class, nor can it inherit from any
 class other than   System.Object .

Factory Method design pattern

What is the Factory Method Pattern?
 •   A creational design pattern that   defines an interface for creating an
 object but lets subclasses decide which class to instantiate .
 •   Promotes loose coupling and greater flexibility by delegating object
 creation to subclasses.
Use of the Factory method design pattern
 •   The Factory method design pattern is used in many areas.
 •   For example, in software development where you need to create different
 kinds of objects like databases.
 •   Imagine you have an application that relies on   different types of reports .
 •   Using the Factory method design pattern, you can   create new reports
 easily without changing the core application code .
 •   This saves time and effort and makes the application more flexible
 and easier to update and maintain.

Why Factory Method design pattern ?
 •   The   factory   method   design   pattern   might   seem   like   extra
 complexity   at   first   glance,
 •   but   it   offers   several   advantages   that   make   it   worthwhile :
Why Factory Method design pattern ?
 •   Loose Coupling :
 •   By   using   a   factory   to   create   objects,   your   code   interacts
 only   with   the   interface   or   abstract   class   of   the   object
 being   created .
 •   This   means   you   can   easily   swap   out   different
 implementations   of   the   object   without   modifying   the   rest
 of   your   code .
 •   This   is   a   key   principle   of   object - oriented   programming
 that   promotes   reusability   and   maintainability .
Why Factory Method design pattern ?
 •   Flexibility and Extensibility :
 •   The factory method   allows subclasses to decide which
 concrete class to instantiate .
 •   This makes   your code more flexible and adaptable to
 changes .
 •   You can   easily add new types of objects without modifying
 the existing code that uses the factory.
Why Factory Method design pattern ?
 •   Centralized   Control   over   Object   Creation :
 •   The   factory   method   centralizes   the   logic   for   creating
 objects .
 •   This   makes   it   easier   to   manage   and   control   object
 creation ,   especially   when   you   need   to   perform   additional
 steps   like   logging   or   initialization   during   object   creation .
Why Factory Method design pattern ?
 •   Decoupling from Concrete Classes :
 •   The code that uses the   factory method doesn't need to
 know about the specific concrete classes   of the objects
 being created.
 •   This   makes your code more readable and easier to
 understand .

Static method/object
 •   In C#, a static method is a   member that belongs to the class itself rather
 than to a specific instance (object)   of the class.
 •   This means you can   call the method directly using the class name   without
 creating an object.
 •   Key Features
 •   No Instantiation : You cannot create an object of a static class using the new keyword.
 •   Direct Access : Members are accessed directly via the class name (e.g.,
 ClassName.MethodName ()).
 •   Static Members Only : All fields, methods, properties, and events within the class
 must also be declared as static.
 •   Implicitly Sealed : It cannot be inherited by another class, nor can it inherit from any
 class other than   System.Object .

What is the Prototype Pattern?
 •   The Prototype Pattern allows you to   clone an existing object   rather
 than creating a new one from scratch.
 •   It provides a way to   create duplicate objects while keeping
 performance in mind .
Use
 •   Creating a new   object is   costly or time - consuming .
 •   You   want to clone existing objects , potentially   with slight
 modifications .
 •   You want to   avoid the cost of creating new instances   (like parsing,
 setting up connections, large configurations).
 •   You need to   duplicate complex objects .
 •   You want to   abstract away the instantiation logic   from the client.
Structure
 •   Prototype   (interface) :   declares   a   Clone()   method .
 •   ConcretePrototype :   implements   the   Clone()   method .
 •   Client :   uses   the   prototype   to   create   copies .
Example
 public   interface   IPrototype < T >   {
 T Clone ();
 }
 •   T is a   type parameter : it stands for   a generic type .
 •   You can think of it like   a placeholder for a real data type   (like int, string, House,
 etc.) that   will be specified later when you implement   or use the interface.
 •   This   makes the interface reusable   for any class.
 •   no cast needed (unlike declaring object)
 public interface   IPrototype
 {
 object Clone();
 }
 var cloned = (House) house.Clone (); // need a cast
Example (Cont.)
 public   class   House   :   IPrototype < House >   {
 public   int   Windows   {   get ;   set ;   }
 public   bool   HasGarage   {   get ;   set ;   }
 public   bool   HasPool   {   get ;   set ;   }
 public   House Clone ()   {
 return   ( House )
 this . MemberwiseClone ();   //   shallow copy
 }
 public   void   Show ()   {
 Console . WriteLine ( $ "House: {Windows} windows,
 Garage: { HasGarage }, Pool:   { HasPool }" );
 }
 }
Example (Cont.)
 public   class   LuxuryHouse   :   House   {
 public   bool   HasSwimmingPool   {   get ;   set ;   }
 public   bool   HasGarden   {   get ;   set ;   }
 public   override   House Clone ()   {
 return   ( LuxuryHouse ) this . MemberwiseClone ();
 }
 public   override   void   Show ()   {
 base . Show ();
 Console . WriteLine ( $ "Luxury features → Pool:
 { HasSwimmingPool }, Garden: { HasGarden }" );
 }
 }
Example (Cont.)
 class   Program   {
 static   void   Main ()   {
 LuxuryHouse   luxury   =   new   LuxuryHouse   {
 Windows   =   10 ,   HasGarage   =   true ,   HasSwimmingPool   =   true ,
 HasGarden   =   true   };
 // downcast to access   luxury features
 LuxuryHouse   copy   =   ( LuxuryHouse ) luxury . Clone ();
 copy . HasGarden   =   false ;
 luxury . Show ();
 Console . WriteLine ( " ----   Cloned   ---- " );
 copy . Show ();
 }
 }

Façade Design Pattern
Façade
 •   Provide   a unified interface to a set of interfaces   in a subsystem.
 •   Façade defines a higher - level interface that makes the subsystem easier to
 use
Applicability
 •   you want   a simple interface to a complex subsystem
 •   Subsystems often get more complex as they evolve
 •   this makes the subsystem more reusable and easier to customize,
 •   but it also becomes harder to use for clients that don't need to customize it
 •   A façade   can provide a simple default view of the subsystem   that is good enough for
 most clients
 •   Only clients needing more customizability will need to look beyond the façade
 •   there are many dependencies between clients and the implementation
 classes of an abstraction
 •   Introduce a façade to decouple the subsystem from clients and other subsystems
 •   you want to layer your subsystems
 •   Use a façade to define an entry point to each subsystem level
Structure
 •   Façade
 •   knows which subsystem classes are responsible for a request
 •   delegates client requests to appropriate subsystem objects
 •   subsystem classes
 •   implement subsystem functionality
 •   handle work assigned by the Façade object
 •   have no knowledge of the façade
Consequences
 •   shields   clients   from   subsystem   components
 •   reduces   the   #   of   objects   clients   see
 •   easier   to   use   subsystem
 •   promotes   weak   coupling   between   the   subsystem   and   its   client
 •   can   vary   the   components   of   a   subsystem   without   affecting   clients
 •   reduces   compilation   dependencies
 •   doesn't   prevent   applications   from   using   subsystem   classes   if   they
 need   to .
 •   you   can   choose   between   ease   of   use   and   generality

 •   A code scaffold is a template or skeleton code that helps you quickly
 create structure for an application or component.
 •   It typically includes:
 •   Class/interface definitions
 •   Method stubs

 •   Comments or TODOs as placeholders

 •   Easy Learning
 •   Helps juniors understand structure step - by - step

Chain of Responsibility
Definition
 •   Chain of Responsibility is a   behavioral design pattern   that lets you
 pass requests along a chain of handlers .
 •   Upon receiving a request,   each handler decides either to process the
 request or to pass it to the next handler   in the chain.
Example (The Problem)
Example (The Solution)
Multiple If - Else Statements
 public   class   DiscountHandler   {
 public   string   ApplyDiscount ( decimal   amount )   {
 if   ( amount   >   1000 )   {
 return   "10% discount   applied." ;
 }
 else   if   ( amount   >   500 )   {
 return   "5% discount   applied." ;
 }
 else   {
 return   "No discount." ;
 }
 }
 }
Drawbacks:
 •   Tightly Coupled Logic :
 •   Hard to add, remove, or reorder conditions.
 •   Rigid Code :
 •   Scaling becomes difficult as new conditions are added.
 •   Single Responsibility Violation :
 •   Mixing logic for condition checking and action processing.
Using Chain of Responsibility Pattern
 •   The Chain of Responsibility solves these issues by
 separating conditions into discrete handlers .
The Solution
 public   abstract   class   DiscountHandler   {
 protected   DiscountHandler   _ nextHandler ;
 public   void   SetNext ( DiscountHandler   nextHandler )   {
 _ nextHandler   =   nextHandler ;
 }
 public   abstract   string   Handle ( decimal   amount );
 }
The Solution (Cont.)
 public   class   HighDiscountHandler   :   DiscountHandler   {
 public   override   string   Handle ( decimal   amount )   {
 if   ( amount   >   1000 )   {
 return   "10%   discount   applied." ;
 }
 else   if   ( _ nextHandler   !=   null )   {
 return   _ nextHandler . Handle ( amount );
 }
 return   "No   discount." ;
 }
 }

S.O.L.I.D. Principles
What is S.O.L.I.D?
 •   S.O.L.I.D is an acronym that represents five principles of object - oriented
 programming and code design theorized by   Uncle Bob   (Robert C. Martin)
 by the year 2000.
 ▪   [S] ingle Responsibility Principle
 ▪   [O] pen/Closed Principle
 ▪   [L] iskov Substitution Principle
 ▪   [I] nterface Segregation Principle
 ▪   [D] ependency Inversion Principle
What is S.O.L.I.D?
 •   The principles   actually overlap   each other in   a number of   ways.
 •   They have   different point of view .
 •   Based on the context we choose the principles
What does not support S.O.L.I.D?
 •   These principles will say   nothing about   a large number of SE issues
 •   Resource use
 •   Performance
 •   Security
 •   Deployment
 •   Support
 •   Licensing
Why S.O.L.I.D?
 •   When we use all the principles of S.O.L.I.D in a combined manner, it
 becomes easier for you to develop software that can be managed
 easily.
 •   The other features of using S.O.L.I.D are:
 •   It avoids code smells.
 •   Quickly refractor   code.
 •   Can   do adaptive or agile software   development.
 •   When we use the principle of S.O.L.I.D in your coding, we start writing
 the code that is both efficient and effective.
S   —   Single Responsibility
S   —   Single Responsibility
 •   A class should have   a single responsibility
 •   If a Class has many responsibilities, it increases the possibility of bugs because
 making changes to one of its responsibilities, could affect the other ones
 without you knowing.
 •   Goal
 •   This principle aims to separate behaviors so that if bugs arise   as a result of
 your change, it won’t affect other unrelated behaviors.

 Splitting Class and Method Definitions for Better Organization
What is the partial Keyword?
 •   The partial keyword in C# allows you to   split the definition   of a class, struct,
 or interface across multiple files.
 •   Why It Matters:
 •   Enables code separation between auto - generated and manually written code.
 •   Improves collaboration in teams.
 •   Enhances maintainability of large classes.
 Applies to:
 •   Classes
 •   Structs
 •   Interfaces
 •   Methods (partial methods)
Syntax and Rules
 Declaring a Partial Class:
 public   partial   class   MyClass   {
 public   void   MethodA ()   {   }
 }
 public   partial   class   MyClass   {
 public   void   MethodB ()   {   }
 }
Example
 //   UI   responsibility
 public   partial   class   UserForm   {
 private   void   InitializeComponent ()   {   /* UI setup */   }
 }
 //   Business   logic responsibility
 public   partial   class   UserForm   {
 private   void   ValidateInput ()   {   /* validation logic */   }
 }
Rules:
 •   All parts   must use   the partial keyword.
 •   All parts   must be in the same namespace and assembly .
 •   The compiler   merges all parts into a single class .
When to Use partial?
 •   Best Use Cases:
 •   Large classes with different responsibilities.
 •   Auto - generated code (e.g., Entity Framework, WinForms).
 •   Collaborative team development.
 •   Clean separation of UI and logic.
 •   Avoid When:
 •   The class is small or self - contained.
 •   You don’t use code generators or tooling that requires splitting.

 partial class and optionally implement it in another part .
 •   Used   primarily in code generation scenarios   (e.g., auto - generated EF
 classes).
 •   Compiler   removes the method entirely if no implementation is
 provided .

O   —   Open - Closed
O   —   Open - Closed
 •   Classes   should   be   open   for   extension,   but   closed   for   modification
 •   Changing   the   current   behavior   of   a   Class   will   affect   all   the   systems   using   that
 Class .
 •   If   you   want   the   Class   to   perform   more   functions,   the   ideal   approach   is   to   add
 to   the   functions   that   already   exist   NOT   change   them .
 •   Goal
 •   This   principle   aims   to   extend   a   Class’s   behavior   without   changing   the   existing
 behavior   of   that   Class .
 •   This   is   to   avoid   causing   bugs   wherever   the   Class   is   being   used .

Without OCP   –   Bad Design
 Suppose you’re calculating the area of different shapes:
 public   class   AreaCalculator   {
 public   double   CalculateArea ( object   shape )   {
 if   ( shape   is   Circle c )   return   Math . PI   *   c . Radius   *   c . Radius ;
 else   if   ( shape   is   Rectangle r )
 return   r . Width   *   r . Height ;

 public   class   Circle   {

With OCP   –   Good Design
 Use polymorphism instead of if - else blocks:
 // Base class or   interface
 public   interface   IShape   {
 double   GetArea ();
 }
 // Extend with new shapes without touching calculator
 public   class   Circle   :   IShape   {
 public   double   Radius   {   get ;   set ;   }
 public   double   GetArea ()   =>   Math . PI   *   Radius   *   Radius ;
 }
 public   class   Rectangle   :   IShape   {
 ublic   double   Width   {   get ;   set ;   }
 public   double   Height   {   get ;   set ;   }
 public   double   GetArea ()   =>   Width   *   Height ;
 }
 // AreaCalculator does not change
 public   class   AreaCalculator   {
 public   double   CalculateArea ( IShape   shape )   =>   shape . GetArea ();
 }

 •   In other words:
 •   A   child class must be able to stand in place of the parent class   and still behave
 correctly.

Software Architecture

 and   properties,   and   the   relationships

 of   program   or   system   which   made   up

 •   Architectural   Pattern :
 •   A   concrete   solution   to   a   common   architectural   problem .

Layered Style Architectures
 •   The   program   is   partitioned   into   an   array   of   layers   or   groups .
 •   Layers   use   the   services   of   the   layer   or   layers   below   and
 provide   services   to   the   layer   or   layers   above .
 •   The   Layered   style   is   among   the   most   widely   used   of   all
 architectural   styles .
Uses and Invokes
 •   Module   A   uses   module   B   if   a   correct   version   of   B   must   be
 present   for   A   to   execute   correctly .
 •   Module   A   calls   or   invokes   module   B   if   A   triggers   execution   of
 B .
 •   Note   that
 •   A   module   may   use   but   not   invoke   another
 •   A   module   may   invoke   but   not   use   another
 •   A   module   may   both   use   and   invoke   another
 •   A   module   may   neither   use   nor   invoke   another
Layer Constraints
 •   Static   structure — The   software   is   partitioned   into   layers   that
 each   provide   a   cohesive   set   of   services   with   a   well - defined
 interface .
 •   Dynamic   structure — Each   layer   is   allowed   to   use   only   the
 layer   directly   below   it   ( Strict   Layered   style)   or   the   all   the
 layers   below   it   ( Relaxed   Layered   style) .

Pipe - and - Filter Characteristics
 •   Pipes   are   isolated   and   usually   only   communicate   through

 •   Filters   can   be   modified   and   replaced   easily .

 •   Filters   communicate   only   through   pipes,   which   makes   it
 difficult   to   coordinate   them .
 •   Filters   usually   work   on   simple   data   streams ,   which   may   result
 in   wasted   data   conversion   effort .
 •   Error   handling   is   difficult .
 •   Gains   from   concurrency   may   be   illusory .
