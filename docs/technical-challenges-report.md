# Technical Challenges & Architecture Report: MOLD V2 (Mastery Protocol)

This report details the core engineering challenges, design patterns, and architectural trade-offs resolved during the development of MOLD V2.

---

## 1. The Pragmatic Scaling Paradox & Spatial Coupling

### The Challenge
In modern frontend engineering, developers often over-decouple systems under the assumption that "smaller files are always better." However, hyper-decoupling creates a spatial coupling tax: cohesive logic is scattered across dozens of directories, hooks, and contexts.

In our codebase, the **User Guide Overlay** was decoupled into 15 small files (separate subcomponents, styles, static text steps, and observer configs). This created significant visual and spatial fragmentation:
1. **Developer Velocity:** Modifying a static step required opening 3-4 separate files.
2. **Build and Performance:** Every file import added to Next.js Turbopack compilation tracking and bundle overhead.

### The Resolution
We aligned our solution with the **Operational Excellence** and **Cost Optimization (Human Resource Efficiency)** pillars of the Azure Well-Architected Framework (WAF):
- Consolidated the guide back into **one single, high-fidelity, self-documenting file** ([guide-overlay.tsx](file:///d:/Study/Programming/Projects/finalsv2/finals-qb/components/mold/common/guide-overlay.tsx)).
- Kept the modular parts inside the same file as unexported sub-render functions. This preserved 100% of the stepper logic, custom SVG icons, and `IntersectionObserver` scroll states while reducing file navigation overhead to zero.

## 2. Game Mode Strategy Pattern (Core Engine Scalability)

### The Challenge
MOLD V2 supports 7 distinct learning modes (Speedrun, Survival, Hardcore, Practice, Blitz, Full Revision, Flashcards). Hardcoding specific gameplay rules—such as Survival's progressive lives and ticking question timers, Speedrun's global 5-minute countdown, or Hardcore's strict "Hard only" filters—directly into the React state reducer would result in a massive, fragile, and unmaintainable switch block.

### The Resolution
We decoupled game modes from the core state engine using the **Strategy Pattern**:
- Established a `GameModeStrategy` interface that defines how questions are pooled, how timers tick, and how scoring is computed.
- The React reducer in `game-engine.tsx` delegates these computations directly to the active strategy.
- This keeps the core reducer engine completely closed for modification but open for custom user-created modes.

```typescript
export interface GameModeStrategy {
  id: GameModeId;
  buildQuestionPool: (questions: Question[], config: SetupConfig) => Question[];
  getInitialState: (pool: Question[], config: SetupConfig) => Partial<GameState>;
  onTick?: (state: GameState, dispatch: React.Dispatch<GameAction>) => Partial<GameState> | null;
  onAnswerReveal?: (state: GameState, isCorrect: boolean) => Partial<GameState>;
  hasTimer: boolean;
  timeLimitSeconds: (config: SetupConfig) => number;
}
```

## 3. Bulletproofing the Client-Side Ingestion Boundary (BYOK AI Pipeline)

### The Challenge
To maintain the app's offline-first USP and eliminate expensive backend proxy hosting, we implemented a **Bring-Your-Own-Key (BYOK) AI Pipeline** and a manual copy-paste wizard. Users paste JSON subject payloads directly generated by LLMs (Gemini or Claude). 

Because these AI outputs are completely untrusted, we faced major parser vulnerabilities:
1. **JSON Malformation:** LLMs frequently output unescaped quotes inside technical code blocks or fail to escape mathematical backslashes.
2. **Security Injection:** Malicious HTML payload inputs inside explanations could trigger Cross-Site Scripting (XSS).
3. **Storage Corruption:** Storing invalid question formats would corrupt the browser's `localStorage` namespace.

### The Resolution
We built a strict **Zod Schema & Regex-based Adapter Boundary** inside [subject-persistence.ts](file:///d:/Study/Programming/Projects/finalsv2/finals-qb/lib/subject/subject-persistence.ts) and [subject-importer.tsx](file:///d:/Study/Programming/Projects/finalsv2/finals-qb/components/mold/subject/subject-importer.tsx):
- **Syntactic Auto-Repair:** A regex-based pre-parser captures unescaped backslashes (e.g., LaTeX formulas `\sum` to `\\sum`) and unescaped double quotes inside markdown blocks before invoking `JSON.parse`.
- **Zod Schema Adaption:** Inbound objects are parsed against a Zod schema. If minor key variations occur (e.g. `flashcard` vs `flashcards`), the adapter normalizes it to the core `FullSubjectData` format.
- **XSS Sanitization:** All text strings are processed through `isomorphic-dompurify` on the client side before rendering, neutralizing script injections.

## 4. Stateful Streak Shield & Flame Progression

### The Challenge
Learning retention drops significantly when users feel discouraged. In gamified apps, losing a 25-question streak due to a single typo or click error ("fat-finger mistake") triggers immediate user drop-offs. We needed a mechanism to preserve streaks under specific conditions without creating state inconsistencies (like double-counting correct items).

### The Resolution
We implemented the **Streak Shield** directly into the reducer state machine:
- **Shield Earning:** When the player reaches 5 consecutive correct answers, the reducer sets `streakShieldActive: true`.
- **Shield Activation:** If the user submits an incorrect choice, the reducer checks if the shield is active.
- **State Transition:** If active, the reducer intercepts the error state:
  1. Increments `wrongAnswers` (maintaining statistical accuracy).
  2. Sets `streakShieldActive: false` and `streakShieldTriggeredThisQuestion: true`.
  3. Bypasses the streak reset to `0`, preserving the player's active streak.
  4. Triggers a specialized "Shield Absorbed Error" visual state on the Question Card.

## 5. Offline-First Spaced Repetition (SM-2 Algorithm)

### The Challenge
To support long-term memory consolidation, we integrated a **Spaced Repetition System (SRS)**. Standard web architectures fetch scheduled review lists from a database cron-job. For MOLD V2, all computations had to run locally, offline-first, without lagging the UI.

### The Resolution
We implemented the **SuperMemo-2 (SM-2)** algorithm locally in pure TypeScript:
- Tracks individual terminology and flashcard responses.
- Evaluates ease factors ($EF$) and repetition counts ($n$) on each flip review, writing timestamp intervals directly back to the local subject store.
- Upon session start, a lightweight query builds the active "Study Deck" queue based on items whose intervals have expired, optimizing memory consumption.
