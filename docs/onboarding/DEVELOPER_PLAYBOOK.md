# Developer Playbook

Welcome to the MOLD V2 architecture! This playbook outlines the step-by-step commands and workflows necessary to set up your workspace, validate your localized testing framework, and follow PR rules.

## Initialization Commands

To orchestrate a clean multi-tenant sandbox and bootstrap your environment, run the following commands sequentially:

**1. Install Dependencies**
Ensure you are using `pnpm` to adhere to the repository standards:
```bash
pnpm install
```

**2. Bootstrap the Local Environment**
Spin up the multi-tenant development setup (which initializes docker containers and seeding scripts) using the orchestrator:
```bash
bash scripts/setup/setup.sh --multi-tenant
```

**3. Start the Development Server**
Launch the Next.js local server:
```bash
pnpm dev
```

## Testing Workflows

The repository uses the native `node:test` runner. **Do not use Jest or Vitest.**

**1. Run the Full Test Suite**
To validate all localized tests across game logic, telemetry, and subjects:
```bash
pnpm test
```

**2. Run Type Checking**
The project relies heavily on strict TypeScript. Validate your types without emitting built files:
```bash
pnpm exec tsc --noEmit
```

*Note: The `pnpm lint` and `pnpm format` commands are currently not supported or fail with invalid project directories. Rely on `pnpm test` and `tsc` for validation.*

## PR Validation Rules

When creating Pull Requests or submitting code changes, strictly adhere to the following rules:

1. **Verify Sandbox State:** Ensure that no local `.js` artifacts generated by localized `tsc` compilations are accidentally staged in your PR.
2. **Pre-Commit Checks:** You must successfully pass `pnpm test` and `pnpm exec tsc --noEmit` before proposing a change.
3. **Avoid Destructive State Mutability:** When updating React state arrays, use immutable methods (e.g., `.toReversed()` or shallow copies) rather than mutating the array in place (e.g., `.reverse()`).
4. **Architectural Traceability:** Any modification to `GameState`, `RunRecord`, or `FullSubjectData` must not break existing data contracts. Check the Component Registry and Topology maps in `docs/architecture/` before mutating central interfaces.
